You are given observations of human choices in risky-gamble problems.
Each problem presents two gambles: Option A and Option B. A gamble has outcomes and their probabilities (percent).
You will see a short history of previous trials for the same participant and problem, including chosen option and feedback if available.

You may also be given validation examples and validation log-likelihood scores.
Use the validation information to judge whether the current behavioral rule is too confident or generalizes poorly.

Important validation guidance:
- Validation log-likelihood is usually lower than training log-likelihood. This alone is not a problem.
- The random-choice baseline is around -0.693 log-likelihood per trial.
- Validation scores much worse than this, especially below -1.0, suggest severe overconfidence or poor generalization.
- Example:
    - train = -0.05, validation = -0.16:
      validation is still strong. Do not unnecessarily weaken the behavioral rule.
    - train = -0.05, validation = -1.20:
      validation is poor. The program should reduce overconfident probabilities.

- If validation performance is poor, it is encouraged to include a simple participant-level parameter such as:
    - consistency
    - confidence
    - calibration_strength

- This parameter should represent how predictable or stable the participant is overall.

- IMPORTANT:
  This parameter should NOT be computed mainly from:
    - recent actions,
    - switch rates,
    - or short-term history patterns.

- The local history input may still be used normally for behavioral modeling, but participant-level consistency should remain a separate concept.

- It is acceptable to use a simple fixed constant for participant-level consistency.

Example:
```python
consistency = 0.2
````

* When consistency is low, soften probabilities toward 0.5.

Example:

```python
p = consistency * p + (1 - consistency) * 0.5
```

* The output should still depend meaningfully on the problem inputs.
* Avoid complicated confidence formulas mainly based on local history statistics.
* Never hard-code validation_loglik, train_loglik, or test_loglik inside choose(...).
* Use validation information only to guide the design of the behavioral rule, not as runtime variables.

Write Python code that reproduces the observed behavior. You must generate a program implementing:

def choose(problem, history):
"""
Evaluated by log-likelihood.
Goal: maximize held-out behavioral generalization, using training behavior while respecting validation performance.

```
problem: dict with keys
    - gamble_A: {"probs": List[float], "rewards": List[float]}
    - gamble_B: {"probs": List[float], "rewards": List[float]}
    - option_keys: e.g., ["A","B"]
    - has_feedback: bool
history: list of dicts with keys
    - action: int (0 for A, 1 for B)
    - feedback: float or None
return: float, probability of choosing option 1 (Option B)
"""
```

Requirements:

* Pure Python, no imports, deterministic.
* Use only the provided problem and history.
* Do not call external APIs.
* Do not sample or use randomness.
* Return a single finite float probability of choosing Option B.
* The return value must be strictly inside (0, 1). If needed, clip to a safe range such as [1e-6, 1 - 1e-6].
* Higher returned values mean the participant is more likely to choose Option B.
* Avoid numerical errors such as division by zero, overflow, or invalid operations.
* Some trials may have unknown probabilities: `problem["gamble_A"]["probs"]` or `problem["gamble_B"]["probs"]` can be `None`.
* Your code must handle this safely (do not iterate over `None`; do not assume probabilities are always present).
* If probabilities are missing, use a deterministic fallback (for example, equal weights over listed rewards) and continue returning a valid probability in (0, 1).
* Do not use `pow(...)`; use `**` for exponentiation.
* Keep all helper logic used by `choose(...)` inside `choose(...)` (nested functions are allowed).
* Do not rely on top-level helper functions outside `choose(...)`.
* Ensure every variable used in expressions is defined on all branches (avoid branch-only definitions).

Behavioral requirements:

* Do not return constant or near-constant probabilities (e.g., always close to 0.5).
* Do not add small noise or artificial variation to a constant value.
* The probability must depend meaningfully on the problem inputs.
* History may be used when helpful, but do not rely only on copying or smoothing past actions.
* The program should behave sensibly across different problems and histories.
* When validation performance is poor in absolute terms and much worse than training performance, avoid overly sharp probability outputs.

* If consistency or confidence is used, it should mainly represent participant-level uncertainty, not short-term action patterns.
* If validation performance is poor, lower consistency/confidence should make probabilities softer and closer to 0.5 while still depending on the problem inputs.
* If validation performance supports strong generalization, the program may use more decisive probabilities.
* Do not implement fake validation checks inside choose(...). For example, do not write `validation_loglik = -1.5` or `if validation_loglik < train_loglik: ...`.

Generation requirements:
