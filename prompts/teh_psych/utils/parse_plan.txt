You are given a dataset/task description and representative raw rows from one Psych-101 experiment.

Your task is to produce a parser plan that a fixed Python parser engine can use to convert raw transcript text into structured categorical-choice trials.

You will be given:
1. A dataset/task description, if available.
2. Several representative raw rows or transcript snippets from the experiment.
3. Optional metadata such as experiment_id, split name, row index, participant id, or response columns.

Use the dataset description to understand the task structure, but derive extraction rules from the raw rows. If the description and raw rows conflict, trust the raw rows and mention the conflict in uncertainty_notes.

The parser plan is not the parsed dataset itself. It is an extraction specification.

The downstream structured trials will be used by a cognitive program with this API:

def choose(problem, history):
return {0: p0, 1: p1, ..., K-1: pK}

Therefore, the parser plan must identify:

* trial boundaries
* available options on each trial
* how raw responses map to normalized integer action ids
* the observed target action
* feedback, if available
* block/game/task context, if available
* which trials should be prediction targets
* which trials should be context-only

Output only valid JSON. Do not include markdown, comments, explanations, or code fences.

Important rules:

1. Output JSON only.
2. Do not output parsed trials.
3. Do not invent task details not supported by the raw examples.
4. Prefer simple regexes that match stable transcript phrases.
5. Every action response must map to a normalized integer action id.
6. Action ids must be consecutive integers from 0 to K - 1.
7. The parser should preserve original raw keys in the parsed options, but normalized action ids must be used for `target_action`.
8. If an instructed/demonstration/context trial should not be predicted, define `context_only_trial_rule`.
9. If the task is sequential, define a minimal `state_machine`.
10. If options vary across trials, use `per_trial_available_keys`.
11. If options are fixed for a participant or block, use `fixed_keys_from_instruction` or `per_block_key_list`.
12. If the raw examples are ambiguous, set `human_review_required` to true and explain the uncertainty in `uncertainty_notes`.
13. If the task is not a categorical choice task, still output valid JSON with `"task_type": "categorical_choice"`, set `"human_review_required": true`, and explain why it may be unsuitable in `uncertainty_notes`.

Guidance for common cases:

* If each trial is simply one line like “You press <<F>>”, use `boundary_strategy = "one_press_per_trial"`.
* If each trial has stimulus lines followed by a press line, use `boundary_strategy = "stimulus_then_press"`.
* If a transcript line contains multiple `You press ...` decisions, the engine splits at sentence boundaries; each decision must use only the options available at that decision (derive options from the stimulus before that press, not from later presses in the same episode).
* For go/no-go tasks (press vs omit/nothing), use `option_normalization.strategy = "respond_omit"` with binary actions (0=omit, 1=respond). Do not map multiple response keys to the same action id.
* If the transcript has games, rounds, blocks, casinos, decks, or environments, define `block_boundary_rule` and put these fields in `problem.context`.
* If feedback appears as points, reward, win/loss, or correct/incorrect, define `feedback_rule`.
* If the participant is told to press a specific key, do not treat that as a prediction target. Mark it context-only.
* If options are described by key labels, preserve the raw key in each option but map it to integer action ids.
* If choices are numeric keys such as 1 through 8, map them to actions 0 through 7 unless the instruction clearly defines another order.

The final JSON should be compact but complete enough for deterministic parser execution.
